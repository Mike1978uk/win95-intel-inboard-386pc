# T130.MPD: where it polls, and what an IRQ would change

Static read of Adaptec's `drivers/trantor_t130b/T130.MPD` (10,176 bytes, md5 `9cc53279`), for
#42 (is an IRQ worth having?) and #41 (pace the polling). Whole binary disassembled with
`tools/pedis.py`; the sweep covers the one executable section end to end.

**Everything below is read from code, not measured.** The A/B run in `vm_t130b` is what
confirms or kills it.

## Entry points

From `HW_INITIALIZATION_DATA` built at rva `0x482`:

| routine | rva |
|---|---|
| HwInitialize | `0x82F` |
| HwStartIo | `0x8CE` |
| **HwInterrupt** | **`0x9A4`** |
| HwFindAdapter | `0x572` |
| HwResetBus | `0xA9C` |
| HwAdapterState | `0x56D` |
| timer callback | `0x857` |

`docs/next_session_2026_09_26.md` names `0x10A9C` as HwInterrupt. That is HwResetBus.

Registers as the driver uses them (base `0x340`): card control/status at `base+0`, 16-bit data
buffer at `base+4`, NCR 5380 at `base+8`..`base+0Fh`.

## How a command runs

1. **Select** (`0x118E`): wait up to 1 s for bus free, put `80h | (1 << id)` on the data bus,
   assert SEL. **ATN is never asserted**, so no IDENTIFY message is sent and the target cannot
   disconnect. It holds the SCSI bus through its seek. (#31's question, answered for this driver.)
2. **Send the CDB**, then check once for REQ in the expected phase (`0xCAA`). If the target is
   ready, run the rest synchronously; otherwise arm the 5380 (`MR2` DMA mode, card control bit
   `10h`) and return pending.
3. **Wait for the target.** This is the only step an IRQ changes:
   - **IRQ:** HwInterrupt runs when the 5380 raises its flag.
   - **Polled:** a 2 ms `RequestTimerCall` (`0x857`) reads the 5380's IRQ-active bit
     (`base+0Dh` bit 4) once per tick and re-arms.
4. **Data phase, status, message** (`0xCFE`), run from HwInterrupt or the timer callback. Per
   128-byte block: spin on card status `base+0` bit 2, up to 10,000 back-to-back reads, then a
   1 us-stall loop **with no timeout** (`0x17D3`); then 64 word reads from `base+4`. The same
   code runs in both modes.

## The driver decides for itself whether the IRQ works

The timer is armed on the first commands whatever the mode. If the timer finds a completion
the IRQ should have delivered, a countdown of 5 ends in `ScsiPortLogError` code 8
(`SP_IRQ_NOT_RESPONDING`) and it polls from then on. If the IRQ wins 5 times, the driver stops
arming the timer. So in run B, a working IRQ shows as the 2 ms timer going quiet after five
commands.

## What this predicts for #42

- **Bus occupancy:** polling costs one 5380 read (~5.8 us, technique 109) per 2 ms tick, while
  a command waits on the target. About 0.3% of the wait; an IRQ saves only that.
- **CPU:** each tick also costs SCSIPORT's timer dispatch. Not known from the code.
- **Latency:** polled mode sees a finished seek up to one tick late (if SCSIPORT honours 2 ms;
  Win95's timer granularity is not known). This is the one place an IRQ could buy speed.
- **Unchanged either way:** the data phase. It spin-polls the card at interrupt or timer time
  with no yield, and that is where most of the bus time goes. That is #41's target, not #42's.

## Measuring it

Counters in the 86Box T130B model, dumped per copy, separated by what they answer:

| counter | answers |
|---|---|
| reads of `base+0Dh` | timer ticks (polled wait) |
| reads of `base+0` | data-phase ready spin |
| reads of `base+0Ch` | selection/handshake waits |
| word reads/writes of `base+4` | data moved (the control) |

Plus elapsed time and a CPU-bound loop running beside the copy. The prediction is right if
`base+0Dh` reads drop to near zero in run B while `base+0` reads stay about the same.

## Run A — polled, as installed (2026-09-26)

`vm_t130b`, `T130.MPD` via our XT INF (`Polling=1`, card `irq = 00`). 86Box built from
`xtcf-lotech-stride2` plus per-register counters (`t130b-ab-counters` `c699d532f`, local
scratch branch). Workload: `C:\T130AB.BAT` copies `C:\WINDOWS\COMMAND` (1,084,558 bytes, 40
files) to the SCSI disk three times, deleting the target before each copy.

| | copy 1 | copy 2 | copy 3 |
|---|---|---|---|
| guest seconds | 7.97 | 7.36 | 6.87 |

All 40 files byte-identical on the SCSI image, checked from the host.

**No ATN, ever:** 52,077 writes to the 5380 initiator command register, none with ATN set.
The driver never sends IDENTIFY, so no target can disconnect. Confirmed live.

**T130B accesses over the copy window** (all three copies):

| | count | real-5160 cost |
|---|---|---|
| data bytes written (word I/O) | 3,152,896 | × 3.819 us = **12.0 s** |
| register reads + writes | 212,099 | × 5.695 us = **1.21 s** |
| of which 5380 bus-status reads (`base+0Ch`, handshakes) | 57,074 | 0.33 s |
| of which card-status reads (`base+0`, block-ready spin) | 53,630 | 0.31 s |
| of which 5380 IRQ-flag reads (`base+0Dh`, the polled wait) | 1,826 | **0.010 s** |

Costs use the per-access figures measured on the real 5160 (techniques 109, 128). 86Box does
not model bus hold time (#43), so its own timings cannot show these; the counts can.

- **The polled wait is under 1% of the driver's register traffic.** In the emulator the target
  answers at once, so each command's wait is about one tick; on hardware a seek adds roughly
  one read per 2 ms of seek. Still small.
- **The card-status spin is about two reads per 128-byte block here**, because the emulated
  card never makes the driver wait. On hardware it will be higher and cannot be measured in
  86Box.

**Idle traffic, unasked-for:** with nothing running, the driver makes ~790 accesses every
~2 s (548 reads, 242 writes, `base+0Ch` 282 of them). That is ~4.5 ms of bus per 2 s, about
0.2% continuous, plus an L1 flush per access (#41). Most likely Windows polling the SCSI CD-ROM
for media; not yet confirmed. On the 5160, with more targets, it would be larger.
