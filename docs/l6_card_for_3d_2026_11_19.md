# L6: the whole card for 3D (2026-11-19)

Owner, 11-19: "we need to make use of the unused silicon ... the more work the card does the less time on the bus,
the less cpu cycles". Worklist L6. Cost unit: one port write, ~7.6 us on the 5160.

## (a) Census: writes for one triangle by polygon fill (`tools/dos3d/m8dos.c` `batch_flush`)

| Job | Writes | Notes |
|---|---|---|
| Outline into the scratch plane | 16 | `WRT_MASK` + 5 an edge (`LINEDRAW_INDEX` + 4 coordinates), each edge sent top to bottom on its own |
| Fill blit from the scratch plane | 11 | `DESTX_DIASTP`, `DESTY_AXSTP`, `SRC_X_START` are the same for every polygon |
| Outline again on the visible page | 9-10 | colour (if changed), `LINEDRAW_INDEX`, 2 a corner + the closing corner |
| Batch set-up, restore, scratch clear (shared by up to 8) | ~2.5 | |
| Total | ~40 | card bench: 2,002 writes a frame for 50 triangles + clear (`captures/2026-11-19_c3_card/`) |

Polygon cost does not depend on its size: the engine fills the pixels. The edges are not the main cost.

## Retrospective against the Windows driver

- P2 applies to `drivers/mach8_display/src/m8d3d.c`: three outline loops send edges one by one (~1249 triangle,
  ~2032 rows-reached edges, ~3122 joined patches). The first is a closed triangle (direct); the other two draw
  partial edges or patch edges, so each needs its own check. Through `docs/mach8_driver_method.md` (card cycle,
  benched twice): the bed does not model the polygon fill (X27).
- P1 matches the Windows code already (it sends the fill registers every time).

## Compression on the card's terms

- **Bus:** mono expansion (DP_CONFIG mono, = bed byte for byte, L4c) takes 1 bit a pixel through the FIFO: 16 pixels a
  word write against 2. Today: Windows text. For 3D and DirectXT: HUDs, fonts, masks, few-colour sprites (one pass a
  colour). Spans are the run-length form (3 writes a run).
- **Card RAM:** the polygon fill already keeps 8 one-bit images in one byte-plane (one a bit, chosen by RD_MASK).
  The same holds 8 cached masks in the space of one 8 bpp image; one blit expands any of them.
- SWAPCOMP-style compression does not carry over: the engine cannot decompress arbitrary data.
- Asm: the cost is port writes, not CPU; m8dos's send loop is already inline asm. DirectXT's page compare is the
  CPU-heavy part (rep cmpsd over rows).

## P4: hardware depth test (2026-11-19, card, `ZPROBE.TXT`)

`m8_depth(z)` in m8dos: pixel value = depth x 16 + colour (16 colours a depth band; the palette shades each band). Per
polygon `COLOR_CMP` (B2E8h) = z x 16 and `DEST_CMP_FN` (EEEEh) code 18h "screen < COLOR_CMP" keeps any nearer pixel;
compare off for the scratch outline and clear. `M8DTEST zprobe`: 15 overlapping triangles, one a depth, 4 frames.

| Frame | Far to near, no test (reference) | Random order + test | Near to far + test | Random order, no test (control) |
|---|---|---|---|---|
| 0 | 625 writes | identical, 671 | identical, 671 | 3,045 px differ |
| 1 | 592 | identical, 654 | identical, 633 | 7,177 px differ |
| 2 | 610 | identical, 633 | identical, 654 | 7,574 px differ |
| 3 | 644 | identical, 692 | identical, 692 | 2,224 px differ |

The compare applies to the polygon-fill blit and to the line draw (both unmeasured before). ~3 writes a triangle.
Per-pixel occlusion with no CPU sort, 16 levels; ties go to the later polygon, as painter's order.

Retrospective: the Windows 8 bpp HAL reports no Z (`contexts ... with Z 0`) although twist sends ~10,000 Z triangles
(`tris ... z 10448`); P4 is its route to a real 16-level Z test (colour budget: 16 a band at 8 bpp). Worklist L6.

## Where a frame's time goes, and the clear sent early (2026-11-19, card)

`M8DTEST costs` (`COSTS.TXT`, before): clear + 50 triangles 26.36 ms; 50 triangles, no clear 21.42 ms; clear only 4.67 ms
(7 writes, ~15 ns a pixel). The two add up: the engine cleared while the CPU waited (779 status reads a frame). Most
status reads are that waiting, not overhead. Change: `m8_clear` sends the page clear at once when the page is off
screen (vsync off, or the last flip already done), so the engine clears while the frame is built (`CL_M8PROBE.TXT`):
clear + 50 triangles **21.42 ms, 46.68 fps** (from 37.93); pixels identical on the 8 probe frames; vsync-on bench
unchanged at 28.67 fps (21.4 ms is still over one 17.6 ms refresh). Since this morning: 34.7 -> 46.7 fps vsync off.

## P3b: what the fill leaves out (2026-11-19, card, `EDGE.TXT`)

`M8DTEST edgeprobe`: 8 separate triangles of every orientation, two neighbours sharing an edge and a quad, drawn with and
without the page outline (`M8_OPT_NOOUTLINE`, probe only) and read back. Per shape, its boundary pixels in the
reference by side, and how many are missing without the outline: **every right-edge pixel** of every shape; left
edges all present but the apex rows (2 a shape); top and bottom rows missing where they are edges (the blit covers rows
strictly between top and bottom); no inside pixel missing. The first neighbour's right edge is covered by the second's
fill (1/130 missing). So the fill is left-inclusive, right-exclusive on a row: half of Direct3D's top-left rule.

Next (P3b proper): fill rows top..bottom-1 (`CUR_Y` = top, source from scratch row 0) with the top-down chains as the
scratch outline (an apex row gets two pixels that cancel, not one), and no page outline: ~-7 writes a triangle net,
shapes drawn by the top-left convention (no right column, no bottom row), meshes tiling exactly so neighbours can
share a batch. Check: a mesh grid with no holes and no overlaps, then writes and fps.

## P3b result: the top-left rule is the default (2026-11-19, card, `TILE.TXT`, `REG.TXT`)

Fill from the top row to the row above the bottom, scratch outline as top-down chains, no page outline. A jittered
mesh of 160 triangles: no background pixel inside and forwards = backwards pixel for pixel (each pixel in exactly one
triangle); under the outline rule forwards and backwards differ by 13,080 pixels. With no page outline, overlapping
fills share a batch (they layer in submission order); only spans or the outline rule force a new one. Mesh writes:
outline rule 7,285; top-left 6,273; **top-left + shared batches 4,335 (-40 %)**. Bench 50x40 vsync off **55.2 fps,
18.1 ms** (outline rule 47.9). Regression after the change: depth test exact (`zprobe`), outline-rule probe identical,
16-bit build the same. The outline rule stays as `M8_OPT_OUTLINE`. Shapes now lose their right column and bottom row:
Direct3D's own rule.

- **P5 (owner, 11-19): a texture made of lines.** The fill toggles at each boundary pixel on a row, so a tiling's edges
  drawn once into one scratch plane and one fill blit colour alternate tiles: a 16x16 checkered floor in perspective is
  34 lines and one or two blits against 256 quads (~7,700 writes). Clean two colours need even-degree vertices
  (squares, bricks, triangle grids); Penrose / Ammann-Beenker / einstein "hat" tilings have odd vertices: probe, do
  not assume. Shared edges drawn once halve the lines for any edge-to-edge tiling.
- **P5b (owner, 11-19): aperiodic tilings as a texture that never repeats.** For tilings with odd-degree vertices,
  colour the tiles (Penrose rhombs 3-colourable; any planar map needs at most 4), one scratch plane a colour: within a
  plane no two tiles share an edge, so the toggling fill fills each tile exactly. Each edge is still drawn once, with
  WRT_MASK = the planes of the two tiles beside it. Cost: one line an edge plus one fill blit a colour, whatever the
  tile count. Probe order: checkerboard (one plane), then a Penrose patch (3 planes); open: two same-colour tiles
  touching only at a corner.

## Fine mesh: the span path broke the rule, fixed (2026-11-19, card, `REG2.TXT`, `REG3.TXT`)

A jittered mesh of 2,560 small triangles under the top-left default (`3ddd594`) had 1,300 holes and forwards/backwards
differed by 9,280 pixels: triangles under ~14 rows went by spans, whose rows are worked out on the CPU and whose
inclusive ends did not follow the rule. Fix: under the top-left rule every polygon the scratch can take goes by fill;
spans (1-2 row slivers, polygons larger than the scratch) leave out the bottom row and each row's last pixel. After:
0 holes, forwards = backwards, and fewer writes (82,708 -> 67,110; outline rule 113,659: -41 %). The 160-triangle mesh
4,195 writes. Depth test, outline-rule probe and both builds unchanged; bench 54-55 fps, 18.1-18.4 ms.

Register probe (`REG2.TXT`, one register left out against the default, 3 random frames each): only SRC_X_START is kept
from one fill to the next (pixels identical when sent once a batch, now built in); CUR_X, DEST_X_START, DESTX_DIASTP
and DESTY_AXSTP must go with every fill (without DEST_X_START the bench also slows to 30 ms a frame).
