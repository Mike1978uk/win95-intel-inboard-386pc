# L6: the whole card for 3D (2026-11-19)

Owner, 11-19: "we need to make use of the unused silicon ... the more work the card does the less time on the bus,
the less cpu cycles". Worklist L6. Cost unit: one port write, ~7.6 us on the 5160.

## (a) Census: writes for one triangle by polygon fill (`tools/dos3d/m8dos.c` `batch_flush`)

| Job | Writes | Notes |
|---|---|---|
| Outline into the scratch plane | 16 | `WRT_MASK` + 5 an edge (`LINEDRAW_INDEX` + 4 coordinates), each edge sent top to bottom on its own |
| Fill blit from the scratch plane | 11 | `DESTX_DIASTP`, `DESTY_AXSTP`, `SRC_X_START` are the same for every polygon |
| Outline again on the visible page | 9-10 | colour (if changed), `LINEDRAW_INDEX`, 2 a corner + the closing corner |
| Batch set-up, restore, scratch clear (shared by up to 8) | ~2.5 | |
| Total | ~40 | card bench: 2,002 writes a frame for 50 triangles + clear (`captures/2026-11-19_c3_card/`) |

Polygon cost does not depend on its size: the engine fills the pixels. The edges are not the main cost.

## Probes, in order (bed first: the bed equals the card on CMD fills; card for timing)

| # | Question | If yes | Saves a triangle |
|---|---|---|---|
| P1 | Do `DESTX_DIASTP`, `DESTY_AXSTP`, `SRC_X_START` keep their values across fill commands? | write them once a batch (a register shadow) | 3 |
| P2 | Does `LINEDRAW_POLY` mode accept a connected outline (index once, 2 writes a corner) with edges in any direction, and fill the same? | outline in one run | ~6 |
| P3 | Can the fill include the boundary pixels, so the second outline goes? | drop the visible outline | ~9 |
| P4 | Hardware depth test: pixel = depth x 16 + colour, `COLOR_CMP` = polygon depth, `DEST_CMP_FN` "keep if dest <" (measured 10-10 on CMD fills, both operands WRT_MASK-masked) | per-pixel occlusion with no CPU sort; palette gives depth fog | -1 (adds one); gains correctness |

P1-P3 together: ~40 -> ~21-25 writes a triangle, close to twice the triangles a second. P4 trades colours (16, or
32 with 8 depth levels) for correct overlaps. Then (c)-(g) of L6.

## Retrospective against the Windows driver

- P2 applies to `drivers/mach8_display/src/m8d3d.c`: three outline loops send edges one by one (~1249 triangle,
  ~2032 rows-reached edges, ~3122 joined patches). The first is a closed triangle (direct); the other two draw
  partial edges or patch edges, so each needs its own check. Through `docs/mach8_driver_method.md` (card cycle,
  benched twice): the bed does not model the polygon fill (X27).
- P1 matches the Windows code already (it sends the fill registers every time).

## Compression on the card's terms

- **Bus:** mono expansion (DP_CONFIG mono, = bed byte for byte, L4c) takes 1 bit a pixel through the FIFO: 16 pixels a
  word write against 2. Today: Windows text. For 3D and DirectXT: HUDs, fonts, masks, few-colour sprites (one pass a
  colour). Spans are the run-length form (3 writes a run).
- **Card RAM:** the polygon fill already keeps 8 one-bit images in one byte-plane (one a bit, chosen by RD_MASK).
  The same holds 8 cached masks in the space of one 8 bpp image; one blit expands any of them.
- SWAPCOMP-style compression does not carry over: the engine cannot decompress arbitrary data.
- Asm: the cost is port writes, not CPU; m8dos's send loop is already inline asm. DirectXT's page compare is the
  CPU-heavy part (rep cmpsd over rows).

## P2 re-checked against the Windows driver's warning (2026-11-19)

`m8d3d.c` `m8d3d_edges` (commit `065a3ac`, 11-05) says a closed outline can put three pixels on the middle vertex's
row so the fill runs on. No capture or handoff records it being seen. The first P2 probe could not have caught it: the
bench's triangles all have the same shape and winding. Second probe (`PROBE2.TXT`, `PROBE3.TXT`): the per-edge
outline as reference against the closed figure and against two top-down chains, read back frame by frame - 4 frames of
random convex polygons (3-8 corners, both windings, ~160) and 4 frames of 120 shallow triangles each with the middle
vertex left or right, either winding (480). **Closed and chains identical to the reference on every frame.** Counting
agrees: with LAST_OFF every row between top and bottom gets two boundary pixels whichever way the edges run.

| Outline | Writes, random frames | Bench 50x40 nv |
|---|---|---|
| Per edge (5 an edge) | 1,910-2,034 | 34.7 fps, 2,002 writes |
| Two top-down chains | 1,669-1,806 | 36.1 fps, 1,859 writes |
| Closed (default) | 1,571-1,726 | 38.3 fps, 1,714 writes |

Kept: closed. Per edge and chains stay as `M8_OPT_EDGES` / `M8_OPT_CHAINS` for later probes. The `m8d3d.c` comment is
contradicted by the card; it is corrected with the Windows P2 change, which still goes through the card cycle.

## P2 in the Windows driver (2026-11-19, card)

`m8d3d.c` `m8d3d_edges` (the 8 bpp HAL triangle) now sends the closed figure: 14 writes instead of up to 20. Installed as
`M8P2.DRV` with `install_h.ps1` (md5 on the card = build: DLL `90E3092D...`, DRV `0078C143...`). Bench: DX5 SDK twist,
`twist_card.ps1`, census reads 60 s apart, ~123,000 triangles between them in each run.

| Run | fps | Whole frame | In Flip (card) | Our code |
|---|---|---|---|---|
| Reference (driver before) | 6.61 | 151 ms | 32.5 ms | 31.1 ms |
| New, run 1 | 6.73 | 148 ms | 29.9 ms | 31.8 ms |
| New, run 2 | 6.75 | 148 ms | 30.9 ms | 30.9 ms |

The card's share of a frame falls ~2 ms; the frame barely moves because twist is spent in our describe and feed
code, not in outlines. M8D3DF (16 bpp, software Direct3D) does not reach this path. Left: the two other outline loops
(~2032 rows-reached edges, ~3122 joined patches). M8D3DF in grab mode hung the card once this session
(`p2base`, before the new driver was installed): grab is not to be used unattended until that is understood.
