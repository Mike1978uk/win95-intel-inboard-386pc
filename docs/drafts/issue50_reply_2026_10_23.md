Thanks Andrew - I appreciate the CH376 links and the two ages2001 repositories. None of them will run here as they stand (WINDISK and WINUSB want PCI and a Pentium), but that isn't where their value is: they show what can be done and how someone else solved it. WINDISK already gave us a list of ideas for the XT-CF driver in #52 - retry with a soft reset, media change tracked by a generation counter, real sense data - and its media-change handling is the model for the BlueSCSI hot-swap question below. From WINUSB I want to see how it presents USB mass storage and HID to Windows 9x, because that is the same question as what the Pi should present on the SCSI side. And the CH376's file-level access is a different angle on #51: let the chip do the FAT work and move only file data across the bus. All recorded in docs/resources_and_sources.md.

On the MSRs: XTOUT (MSR 1000h bit 12, wait for READY after OUT) is already cleared on the card, which gave 1.1% in FastDoom. SNP hangs the 5160. Neither SW1 nor flush snooping stops the per-I/O L1 flush we measured on 09-21 (3.24x slower on a 1 KB working set). Turning the cache off around an OUT string needs WRMSR at ring 0 and the display driver runs at ring 3, so per call it would cost a VxD call, which is more than it saves.

Your point that I/O flushes the cache is the lead. None of the Mach8 work had accounted for it. Compiler flags alone do nothing: -os is neutral on the card (1.268x ATI against 1.274x), as -ox was. What matters is how much code and data is touched between port accesses, because each access throws the cache away. The old path sent each register write through its own call, so every write was followed by several line fills. The fill path now decides every write first and sends them all from one short loop, and skips the data path registers when they still hold its own values: 1.288x ATI overall, identical pixels in all 35 tests. The same shape goes into the copy, span and line paths next.

Yes, the timing and correctness fixes will go to 86Box once the driver work settles.

On BlueSCSI hot-swap: my thought is that the Pi keeps a fixed removable LUN and reports a media change through sense data (no medium, then UNIT ATTENTION), as Zip and SyQuest drives do - and as WINDISK tracks it - so Win95 checks on access rather than polling.
