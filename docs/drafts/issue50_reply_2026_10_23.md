Thanks Andrew - I appreciate the CH376 links and the two ages2001 repositories. I have recorded them as references in docs/resources_and_sources.md, with a note that WINUSB and WINDISK need PCI and a Pentium so cannot run on the 5160.

On the MSRs: XTOUT (MSR 1000h bit 12, wait for READY after OUT) is already cleared on the card, which gave 1.1% in FastDoom. SNP hangs the 5160. Neither SW1 nor flush snooping stops the per-I/O L1 flush we measured on 09-21 (3.24x slower on a 1 KB working set). Turning the cache off around an OUT string needs WRMSR at ring 0 and the display driver runs at ring 3, so per call it would cost a VxD call, which is more than it saves.

Your point that I/O flushes the cache is the lead. None of the Mach8 work had accounted for it. I am testing a size-optimised build (-ox was neutral) and reshaping the per-call path so all the memory work happens before the first OUT and the writes then go back to back from registers. Results to follow.

Yes, the timing and correctness fixes will go to 86Box once the driver work settles.

On BlueSCSI hot-swap: my thought is that the Pi keeps a fixed removable LUN and reports a media change through sense data (no medium, then UNIT ATTENTION), as Zip and SyQuest drives do, so Win95 checks on access rather than polling.
