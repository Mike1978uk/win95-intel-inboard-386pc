# Mach8 unused silicon: audit against the bench gaps (2026-10-22)

Static read of the docs and driver source only; nothing run. "Driver" = `drivers/mach8_display/src` (m8hw.c, m8.h, screen.c). A grep of m8.h/m8hw.c finds none of: 92EE/EAEE, EEEE, 9EE8, C6EE, CMD 5, B2EE/BEEE/C2EE, A8/A9, CRT_OFFSET. In use: PATT_DATA (m8hw.c:366, 604), LINEDRAW (m8hw.c:623), LINEDRAW_OPT (611), COLOR_CMP register in the cache table (m8hw.c:70, as a setup register, not exploited). Port-write costs: 7.64 us each on the card, so "writes" below is the unit.

## Gaps with no lever yet

- stretchblt 0.26, stretch_dib 0.32: ATIM8 has its own path (seg14 StretchBlt, seg12 DibToDevice) which the disasm doc covers only in outline: seg14 not traced. Read seg14 before judging. No unused-silicon lever fits; the work is the row-replication/skip logic.
- cursor_move 0.46: ATIM8 saves and restores a 32x32 via VRAM-to-VRAM and `rep outsw` (seg01:0e00-1300); not traced whether it parks images off-screen. Ours does the same (screen.c:469-498) plus two mono blits (AND, XOR); the gap is probably writes, not a lever.
- ellipse 0.61: ATIM8 forwards it to DIBENG. Gap is span-fill write count (our fills per span).
- getpixel 0.61, setpixel 0.72: ATIM8 Pixel path (`PixEngine`, seg01:1e56); setpixel is a 1x1 fill; getpixel is a 1x1 read. Per-call overhead, not silicon.
- dib_8bpp 0.61, mono_bmp 0.65, text_varied 0.65, mem_to_mem 0.66, rectangle 0.79: ATIM8 uses a run-time generated `rep outsw` stub (seg16:45ca) and a per-glyph FIFO budget. These are host-side technique gaps (stub, glyph cache), not hardware.
- fill_small 0.90, blit_small 0.92: setup-write count; already at near parity.

## Retro candidates

- Dithered/hatched fills (just built): per-row DEST_Y_END with linear mono pattern uses 3 writes per row; ATIM8's colour-brush (8 rows then one VRAM copy) shows the replication copy as an alternative for tall fills.
- Dashed pens (`565ec61`): LINEDRAW bounds could give the redraw box with no CPU maths if a polyline ever falls to read-back.
- Bitmap cache (11-26x): packed storage via the extended source stream would let more sprites fit in the 128-row strip below the screen at 1024x768 (bmp_large 11x gap is room, not speed).
- Cursor: a colour-compare transparent blit could replace the AND+XOR double mono pass if a cursor-save area holds a key colour. Unverified.
- Floodfill: dest compare fill (EEEE) is the only candidate, and it is unconfirmed.

Unverified throughout: no cost figures exist for source compare in an icon draw, nor for compare floodfill; none of this has been run on the card.
