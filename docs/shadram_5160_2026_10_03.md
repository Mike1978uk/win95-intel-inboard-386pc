# SHADRAM and the DMA buffer on the 5160 - 2026-10-03

Two idle 30 s `PERFLOG` captures after boot, with `SWAPCOMP`, `SHADRAM` and the 16 KB DMA
buffer (`DMABufferSize` removed) all in place. Between them the owner set Hard Disk and CD-ROM
read-ahead to none and rebooted. Raw: `docs/captures/2026-10-03_5160/`.

## SHADRAM: no pages on the real card

| counter | value, both boots |
|---|---|
| `Status` | 0 (Windows did not own the pages; the window and ROM areas mapped) |
| `PagesTested` | 16 |
| `PagesFailed` | 16 |
| `PagesAdded` | 0 |

Every page of `0x5E0000`-`0x5EFFFF` failed the pattern test: either the pattern did not read
back, or writing it changed `C0000` or `F0000` at the same offset. The driver does not record
which. The address came from the emulator model and UniPCemu, not the real card; the bed result
(16/16, page-ins -13.8%) therefore says nothing about the 5160. The safety design worked: a wrong
address cost the pages, not the machine. Windows ran normally on both boots.

Next, to choose between "no RAM / write-protected there" and "an alias of a live ROM area": a
build with one counter per failure reason, one boot. Until then `SHADRAM.VXD` adds nothing and
can stay loaded or come out; it holds a 4 KB save buffer.

## DMA buffer 64 -> 16 KB: consistent with the 48 KB, not proven

Locked memory less the disk cache (System Monitor's `cpgLocked` includes the cache,
`docs/driver_audit_2026_09_28.md`):

| capture | locked excl. cache |
|---|---|
| 2026-10-02, `SWAPCOMP` on, 64 KB buffer (`PL_B1`, `PL_B2` first rows) | 1,304 KB |
| 2026-10-03, 16 KB buffer, read-ahead on | 1,260 KB |
| 2026-10-03, 16 KB buffer, read-ahead off | 1,264 KB |

About 40 KB lower. The 2026-10-02 captures started mid-workload and differ between themselves by
up to 136 KB (`PL_A1` 1,420, `PL_A2` 1,284), so this is consistent with the expected 48 KB, not a
measurement of it. DOS-box sampled sound and a floppy copy not yet checked.

## Read-ahead off: no locked memory freed

Locked excl. cache 1,260 -> 1,264 KB: the CD-ROM cache setting does not hold locked memory here.
Boot page-ins 1,567 -> 1,551. The speed question (#45 row 3) still needs `T130AB` at each
setting; these idle captures cannot answer it.

## Where is the reserved RAM? `PHYSPROBE`, same night

`tools/physprobe/` (unreal-mode DOS probe, run in plain DOS after `INBRDPC.SYS`, A20 on via
HIMEM). Raw: `docs/captures/2026-10-03_physprobe/`.

| address | reads | write test |
|---|---|---|
| `0x5E0000`-`0x5EFFFF` | all `FFFFFFFF` (16384 of 16384 dwords) | does not stick |
| `0x5F0000` | `FF` - the BIOS half too | does not stick |
| `0x540000` (just above extended) | `FF` | - |
| `0xE0000` | `FF` (empty) | - |
| `0x4E0000` | zeros: RAM, so A20 and the probe work | - |
| `0xF0000` | the IBM BIOS (`...COPR. IBM`), served from card RAM | - |

Same with port `A0h` bit 7 set for the reads (`PHYSPROB A`), the switch UniPCemu ties to
"remap ROM high". So after boot, nothing answers anywhere in the reserved window: the card shows
its BIOS copy at `F0000` and keeps the 128 KB out of the CPU's address map. SHADRAM's refusal
was correct.

Al Williams' `MINBRDPC.ASM` "bank `5F0h`" is for MOS, which maps memory through 386 paging and
a `$386.SYS` memory-manager call (`memptr` function 5), so it does not show a CPU address.
`INBRDPC.SYS` must open the window while it copies the BIOS and close it after; the mechanism
is not known. Finding it is desk work on `INBRDPC.SYS`; using the EGA half would then also need
the window left open while Windows runs.

⚠ **Emulator fidelity, alert only:** `86box_full/src/device/inboard386.c` maps `0x5E0000` and
`0x5F0000` permanently. The real card does not, after boot. That is why the bed gave SHADRAM
16 pages. Not changed; owner's call.
