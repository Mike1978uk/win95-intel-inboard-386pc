## 2. ATI Mach8 boot memory test — emulator vs real hardware **[AI-SOURCED]**

> The reason you are seeing a discrepancy between the emulator and your real hardware comes down to
> how the ATI Mach 8's dual-engine architecture (the standard 28800 VGA core and the 38800
> coprocessor core) interacts with memory initialization.
>
> **Why the test triggers in the emulator (but not on real hardware)**
> On real hardware, the card initializes in its standard text/VGA mode using its 512 KB of DRAM. The
> 1 MB of high-speed VRAM dedicated to the Mach 8 coprocessor sits isolated behind its I/O registers
> until a driver kicks it into accelerated 8514/A mode.
>
> Emulators (such as 86Box or PCem) handle video memory allocation fundamentally differently:
> - **The floating/uninitialized RAM trap:** many emulators pre-allocate or map the entire video
>   frame buffer area (including the VRAM) at startup, sometimes initializing that memory space to a
>   sequence of random bytes or non-zero patterns (0x00 vs 0xFF).
> - **The signature trigger:** the Mach 8 extension ROM contains self-test routines (ROM integrity,
>   register, and video memory POST sequences). On boot, the ROM checks specific hardware status
>   flags or registers. In the emulator, because the uninitialized VRAM state or the virtualized
>   co-processor registers return unexpected data patterns, the ROM assumes the hardware
>   configuration has changed or is corrupt, triggering the full interactive diagnostic cycle. On
>   real hardware, the registers cleanly reset to exact default cold-boot states, slipping right past
>   the test threshold.
>
> **How to bypass or short-circuit the test**
>
> 1. **Look for the "secret" EEPROM override.** The Graphics Ultra uses a configuration utility
>    (`INSTALL.EXE` or `SETMACH.EXE` from the original ATI utility disk) that writes configuration
>    profiles directly to an onboard EEPROM chip. Run the official ATI DOS configuration utility and
>    look for an option labelled "Advanced Diagnostics", "Video Test on Boot", or "Co-processor
>    Test". Toggling this off writes a bit to the EEPROM. If the emulator isn't saving changes to the
>    virtual EEPROM file cleanly, it will drop back to checking the RAM manually on every cycle.
> 2. **The Jumper 3 (MEM_SIZE) check.** If the emulator profile is set to a 512 KB card but loading a
>    1 MB ROM (or vice versa), the ROM will flag a size mismatch and run the test continuously to
>    isolate the "missing" banks.
> 3. **The hex patch fix.** Load the ROM image into a hex editor, search for the initialization
>    structure following the standard `55 AA` video ROM signature, locate the sub-routine calls for
>    the 8514-Ultra register/memory diagnostics, identify the conditional jump (`JZ`/`JNZ`) that
>    branches into the memory test screen when a register check fails, and NOP it out (`0x90`) or
>    invert it to short-circuit straight to the standard VGA boot vector.

⚠️ The "28800 VGA core + 38800 coprocessor" architecture description should be checked against the
ardent-tool reference below before being relied on.

## 3. Sound on an 8-bit bus **[AI-SOURCED, except where noted]**

> Getting stable audio under these conditions is tricky because Windows 95 VxDs heavily rely on
> 16-bit high IRQs (IRQ 9–15) and 16-bit DMA channels (DMA 5–7) for high-quality audio mixing.
> Because you are physically bound to an 8-bit bus with only IRQs 0–7 and DMA 1–3 available, standard
> Sound Blaster or Windows sound VxDs will routinely lock up trying to hit non-existent AT cascade
> registers.
>
> **The VxD trap:** with a standard Sound Blaster 16 or clone, the Windows 95 native drivers try to
> hook into protected-mode VxDs that expect an AT architecture.
>
> **The solution:** force Windows 95 to drop back to the real-mode/16-bit standard drivers. Force-
> install an older Windows 3.1 style `.drv` sound driver (Sound Blaster 1.5 or 2.0 8-bit) via
> `SYSTEM.INI` under the `[drivers]` section instead of letting Windows 95 handle it through a modern
> protected-mode VxD stack. This restricts the OS to simple, unmixed 8-bit audio loops that respect
> native 8-bit XT interrupt routing.

On the CT1600 specifically:

> The Sound Blaster Pro 2 (CT1600) is arguably the absolute best choice for this hardware footprint
> since it is natively a true 8-bit ISA card (despite the physical 16-bit layout, it only uses the
> 8-bit section for signals, barring some mixer/CD-ROM edge cases).
>
> Targeting `vmad.vxd` (Virtual DMA Device) is highly tactical. In Windows 95, `vmad.vxd` handles the
> virtualization of the DMA controllers. Because it assumes an AT architecture, it defaults to
> managing two cascaded 8237 DMA controllers (channels 0–3 and 4–7). On your IBM 5160, there is only
> one 8237 controller. If `vmad.vxd` attempts to read/write or virtualize registers for the secondary
> AT controller (ports `0xC0`–`0xDF`), or handles 16-bit DMA page registers inaccurately for an XT
> bus, it will instantly trigger a fatal exception or lock the system the moment an application
> initializes audio.
>
> Questions to answer when back at the bench:
> - Does the `vmad.vxd` patch handle the 8-bit DMA page register differences (XT uses `0x80`–`0x8F`,
>   while AT handles them differently)?

**Outcome: the `vmad.vxd` patch built on this theory FAILED on real hardware.** Evidence photo:

#### 386MAX source — primary-source confirmation, and it is *stricter* than "1 MB"

Cloned to `%USERPROFILE%\RiderProjects\386MAX` (`sudleyplace/386MAX`, GPLv3, Qualitas 1987–97,
original DMA code by Bob Smith, January 1987). Three extractions, all from source:

**1. The XT DMA ceiling is 640 KB, not 1 MB.** `386MAX/QMAX_DMA.INC`:

```
@DMA_PA_XT   equ 000A0000h   ; Maximum physical address for XTs
@DMA_PA_ATLO equ 000A0000h   ; Maximum low physical address for AT-class systems
@DMA_PA_ATHI equ 01000000h   ; Maximum high ...
```

and `386MAX/QMAX_SYS.ASM`, in `MARK_XT` (the "mark as PC/XT present" path):

```
    mov  DMASIZE,@DMA_DSK      ; Use hard disk transfer buffer size (64 KB)
    mov  DMA_MAX,@DMA_PA_XT    ; Mark as maximum DMA physical address
```

`QMAX_EVM.ASM` states the buffer constraints in prose: must be below `DMA_MAX`, physically
contiguous, **must not lie between 640 KB and 1 MB**, and — if ≤ 64 KB — must not cross a 64 KB
boundary. `QMAX_DMA.ASM` enforces it per-page: any PTE at or above `DMA_MAX`, non-contiguous, or
crossing a 64 KB boundary is bounced through a local DMA buffer.

**2. Independent confirmation of the `0x00A0` NMI lead (plan step 5).** The same `MARK_XT` routine:

```
    mov  NMIPORT,0A0h   ; NMI clear I/O port
    mov  NMIENA,80h     ; ... enable value
    mov  NMIDIS,00h     ; ... disable value
```

This is a *second, independent* primary source — alongside Wim Osterholt's port list — that on an XT
port `0xA0` is the NMI enable/disable register. Our `inboard386.c` also claims `0xA0` (`port_a0`).

**3. The channel→page-register mapping, confirmed again** (`INC/DMA.INC`): ch0=`87h` *(not PC/XT)*,
**ch1=`83h`**, ch2=`81h`, ch3=`82h`, ch4=`8Fh`, ch5=`8Bh`, ch6=`89h`, ch7=`8Ah` — the last four
marked *(not PC/XT)*. SB Pro is DMA 1, so its page register is `83h`, as already documented.

`MARK_XT` also sets an XT-specific A20 routine (`A20COM_XT`) — unexamined, but adjacent to the Al
Williams `a20()` correspondence if that thread is ever picked up again.

#### ⚠️ Emulator-side consequence found while checking this — `86box_full/src/dma.c`

86Box *does* model the 4-bit XT page latch, at `src/dma.c:1434`:

```c
dma[addr].page = dma_at ? val : val & 0xf;
```

but `dma_at` is assigned `is286` in `dma_reset_legacy()` (`src/dma.c:1591`), and
`is286 = (cpu_s->cpu_type >= CPU_286)` (`src/cpu/cpu.c:553`). **The Inboard is a 386 in an XT
board**, so `dma_at` is 1 and the emulator hands the guest a full 8-bit page register — 24-bit DMA
reach where the real 5160 has 20-bit.

The project already has the right mechanism for this class of bug: `dma_set_force_xt()`, called by
`inboard386.c:777`, a flag `dma_reset()` never clobbers. But it currently only feeds
`dma_xt8237_active()` (the arbitration/refresh model) — **not** the page-width line above, and not
`dma_reset()`'s `if (!dma_at) dma_m = (dma_m & 0xf0) | 0x0f` XT reset-mask at `src/dma.c:1671`.

**Why this matters for issue #5:** it is a concrete mechanism for why the earlier `vmad` byte-patch
**passed in the emulator and failed on real hardware**. Under emulation a DMA buffer above 1 MB
works; on the real machine the page latch truncates and the transfer lands somewhere else entirely.
Fixing it makes the emulator *reproduce* the bug — converting #5 from a real-hardware-only defect
into one debuggable in place. Fidelity fix in its own right, and a candidate third upstream PR.

**Not yet tested** — stated as a code-level reading, not a verified behaviour change.

**What it does legitimately establish**, which is narrower but still worth having:
- `DMABufferIn1MB=True` with `DMABufferSize=64` / `HardDiskDMABuffer=64` is **tolerated** on this
  exact hardware under Windows 3.11 — it does not destabilise the machine.
- So when testing the same knob under Windows 95 for issue #5, prefer **64** over the previously
  planned 32: same hardware, known not to cause problems.

**What it does NOT establish:** that the machine needs the setting, or that it fixes anything. The
substance behind the #5 lead remains @andrew-hoffman's reasoning plus the 4-bit page latch, not
this file.

**Genuinely notable in the same file, and NOT AI-sourced** — these are Intel's own shipped choices:
- `keyboard.drv=ibkbd.drv` and `keyboard=ibvkd.386` — Intel shipped an Inboard-specific keyboard
  driver *and* VxD for Windows 3.x, the period analogue of this project's custom `VKD.VXD` rebuild
  for Windows 95. Same problem, same two-part shape, solved the same way.
- `device=*vdmad` — the **stock** virtual DMA device, *not* Intel's own `IBVDMAD.386`, even though
  that file ships in the same bundle. So the configuration that works here does not load Intel's
  replacement VDMAD at all. That lowers the priority of the `IBVDMAD` disassembly relative to the
  `SYSTEM.INI` route, and is worth knowing before spending a session on it.
